## 0. 执行摘要

| 维度 | 结论 | 说明 |
|------|------|------|
| **Implementation Closure（软件合同）** | **基本成立，证据表述偏乐观** | 07-30 四个 P0（promote orphan、DSR/PBO bypass、dual publish、unknown-market loss）已在架构与代码层闭合；WORM/lease/quality gate 设计扎实 |
| **业务语义完整闭环** | **未完全闭合** | 自动再训练 DAG 可跑到 `CandidateReady`，但 **shadow 绑定缺失** 与 **归因未下游消费** 使「训练→shadow→晋升」与「归因→再训练」两条主链存在结构性断点 |
| **Operational Activation** | **正确 BLOCKED** | 文档判断准确；authenticated current data、mature labels、完整 retraining cooldown 的真实 ReportOnly shadow 尚未达成 |
| **MLOps 最佳实践** | **治理层优秀，部署自动化不完整** | 人工两步 permit→activate、frozen gate、WORM 审计接近金融级；缺 shadow-bind API、渐进式 rollout、归因驱动 recipe |

**一句话结论**：Phase 11.9 把「研究反馈基础设施」建到了生产级，但 **尚未达到「无人干预即可闭合的自动再训练 + 归因反馈」**。文档 `Implementation Closure=DONE` 对 **软件骨架** 基本成立；对 **业务闭环** 偏乐观。最致命的两处断点是：**训练出的 challenger 无法自动进入 shadow slot**，以及 **Attribution 只封印不消费**。

## 3. 架构 strengths（应保留）

### 3.1 Canonical truth 三层分离

```text
ResolutionObservationInbox (WORM)
  → ExecutionAttemptOutcome (PK = order_intent_id)
  → RecommendationExecutionRollup (全 intent terminal 后封存)
  → TruthFreeze barrier (quarantine/lag 不填 0)
```

| 能力 | 实现 | 评价 |
|------|------|------|
| Unknown market | inbox 保留 + `Quarantined` 重试，cursor 在 inbox 同事务前进 | 相对旧 skip-loss 语义正确 |
| 多 intent | rollup 按确定顺序绑定 attempt hash；cohort 只消费 rollup | 审计 #19 附带项已闭合 |
| Crash recovery | CAS cursor、`ON CONFLICT DO NOTHING`、lease reclaim | producer 测试覆盖较好 |
| TruthFreeze | resolution / attempt / rollup 三类 watermark + typed blocker | fail-closed，unknown 不填 0 |

**关键路径**：`crates/quant-pivot-core/src/execution/outcome_reconciliation.rs`、`crates/quant-pivot-repository/src/postgres/quant/resolution_observation.rs`、`execution_attempt_outcome.rs`、`recommendation_execution_rollup.rs`

### 3.2 Feedback DAG — 13 阶段 closed loop

```text
Trigger → TruthFreeze → Coverage → AttributionPlan → Drift → DatasetSeal
        → Training → Calibration → CPCV → Validation → Comparison → Shadow → Decision
```

- `FeedbackStage::next()` 无旁路；`feedback_stage_dispatcher` exhaustive match
- PostgreSQL scheduler：cadence/cooldown/lease/pause CAS；单实例拓扑与合同一致
- Manual/Scheduled 同 `FeedbackCycleKey`（profile + policy + cutoff + champion + candidate_family）可 idempotent 收敛
- **自动化止于 `CandidateReady`**；permit/activation 永远人工两步 — 设计正确

**Validation 硬门**（DSR/PBO bypass 已修复）：

```rust
// crates/quant-pivot-models/src/domain/ports/feedback_governance.rs
pub const fn is_comparison_eligible(&self) -> bool {
    matches!(self.trial_outcome, FeedbackValidationTrialOutcome::CpcvEvaluated)
        && self.quality_gate_report.passed
}
```

未通过 → `ChallengerRejected`，不得进入 Comparison / Shadow / CandidateReady。

### 3.3 Route governance — 单一 serving authority

| 项 | 状态 |
|----|------|
| 删除 `POST /research/models/{id}/publish` 等 | REST 层 verified absent |

## 4. P0 — 结构性断点（阻塞业务闭环）

### P0-1：Shadow 绑定缺失 — 自动再训练链在 Shadow 阶段必然断裂

#### 现象

Shadow stage 要求 route 上 `shadow_model_version_id` **精确等于** 本 cycle Comparison 选中的新训练 candidate：

```rust
// crates/quant-pivot-core/src/service/feedback_shadow_stage.rs (build_subject)
|| generation.shadow_model_version_id != replay.model_version_id
|| generation.shadow_serving_contract_hash != replay.serving_contract_hash
{
    return Err(Self::invalid(
        "published serving generation differs from eligible F09 subjects, profile, category, or policy",
    ));
}
```

不匹配时返回 **hard Err**，不是 `NoEligibleCandidate` 软终止。

#### 矛盾链

1. **Bootstrap** 只设 champion，不设 shadow（`model_route_bootstrap.rs`）
2. **Activate** 要求 candidate **已是当前 global shadow pointer**；晋升后 **清空 shadow**（`promotion_permit.rs:440-481`）
3. **删除旧 publish/bind API 后，无 governed API 将新训练模型绑到 shadow slot**
4. `ModelRouting` 普通 draft mutation 禁用（仅 rollback / bootstrap / promotion）
5. Shadow observations 来自 report run 时 `model_runner` 的 live shadow inference，依赖 route 上已配置的 shadow pointer

#### 后果（生产自动路径）

```text
Cycle 触发 → Training 产出 ModelVersion_N (新 UUID)
  → Comparison 选中 ModelVersion_N
  → Shadow stage: route.shadow ∈ {None, ModelVersion_{N-1}} ≠ ModelVersion_N
  → cycle hard fail
```

系统测试通过是因为 **测试 helper 在 cycle 前手动 activate config 设置 shadow**（`feedback_shadow_stage.rs::activate_generation`），非生产路径。

#### 与文档矛盾

- §9 Operational Activation 要求「至少一个完整 `retraining_cooldown` 的真实 ReportOnly shadow」
- `model-spec-catalog-guide.md` 写明 `shadow_model_version_id` 是 feedback comparison 用的 global challenger pointer，但 **无绑定 API 文档**

#### 建议（破坏式可接受）

新增唯一 mutation，例如：

```text
POST /research/model-route-shadow-bindings
```

- 输入：`feedback_cycle_id`、`model_version_id`、`expected_policy_generation`、idempotency、reason_code、note
- 时机：Validation 通过后、Shadow 阶段前（或 Comparison succeeded 后立即）
- 事务：原子更新 `ModelRouting.shadow_model_version_id` + audit/outbox/CAS
- DAG：在 Comparison→Shadow 之间插入 `ShadowBind` stage，或由 governed service 在 Comparison succeeded 回调触发

**无此步骤，champion-challenger 在 MLOps 意义上是半成品。**

### P0-2：Attribution → Retraining 未闭合 — 「归因反馈」名实不符

#### 文档声明（11.10 merged §Leakage）

> cycle N 的 recipe planner 只能读取 `available_at <= cutoff` 且属于先前 cycle 的 attribution artifact。

#### 实际实现

1. **`candidate_family` 在 cycle freeze 时从 research profile 冻结**，不读 attribution：

   `crates/quant-pivot-core/src/app/ports/feedback_mutation.rs` — `FeedbackCandidateFamily::try_seal` 来自 profile feedback policy，与 AttributionPlan 无关。

2. **`DatasetSeal` 只消费 `cycle.candidate_family`**（`feedback_learning_stage.rs::dataset_params`），零 attribution 引用。

3. **`list_available()` 仅在构建 `AttributionPlanArtifact.uses` 时调用**（`feedback_governance.rs`）；全仓库 **无 downstream consumer**（dataset/training/drift/decision 均不读 `FeedbackAttributionUse`）。

4. **Drift** 使用 PSI/KS/rank-IC 统计漂移（`quant-pivot-research/src/feedback.rs`），不使用 explanation/counterfactual/association。

5. N→N+1 leakage 规则在 `FeedbackAttributionPlanArtifact::validate()` 与 SQL `list_available` 层 **结构正确**，但 **仅 audit seal**，未 enforced at recipe execution。

#### 后果

Attribution 目前是 **promotion gate 审计附件 + UI 展示**，不是 feedback loop 的 **控制输入**。审计 #19「归因→自动再训练」在 **基础设施层** 闭合，在 **决策层** 仍开环。

#### 建议

- **方案 A**：引入 `AttributionRecipePlanner` — cycle N+1 的 `candidate_family`/feature subset/hyperparams 必须由 N 的 `AttributionPlan.uses` 推导；Drift 与 attribution 信号合并 gate。
- **方案 B**：诚实降级文档 — attribution 定位为 **governance evidence only**，不在 11.9 宣称 recipe feedback；审计 #19 部分闭合需重新表述。

## 5. P1 — 高优先级风险

### P1-1：Scheduler `settle_success` 失败 → 悬挂 lease

```rust
// crates/quant-pivot-core/src/service/feedback_scheduler.rs
Ok(success) => match self.repository.settle_success(lease, success).await {
    Ok(state) => info!(...),
    Err(error) => warn!(...),  // 无 settle_retry，lease 不清，cooldown 未设
},
```

`materialize_scheduled` 已成功写 cycle 后，scheduler 行可能挂 lease 至 TTL；阻塞后续 claim。应 fail-closed：`settle_retry` 或显式 `release_lease`。

### P1-2：UI deep link — `?cycle_id=X` 不显示详情

```typescript
// ui/.../feedback/index.vue
const activeView = computed({
  get: () => (route.query.view === 'cycles' ? 'cycles' : 'overview'),
});
```

详情面板在 Cycles tab（`destroy-on-hidden`）。仅 `cycle_id` 无 `view=cycles` 时后台 fetch 详情但用户见 overview。**运营 deep link 实际不可用。**

**修复**：`cycle_id` 存在时自动 `view=cycles`，或将详情面板提升到 tab 外。

### P1-3：Domain Sources「active」卡片误导

`domain-source-presentation.ts` 中 `crypto`/`weather` 计数 **全部 family 行**（含 stale/blocked），卡片标题为 `activeCursors`/`activeFeeds`。与 Phase §7「不把 declared count 标为 active」**直接冲突**。

### P1-4：Governance RBAC 无职责分离

issue permit 与 activate 共用 `publication:publish`。MLOps maker-checker 要求分责；当前同一 super_admin 可秒级自批自激活。

**建议**：`publication:authorize`（issue）vs `publication:activate`（activate），或 distinct acting roles。

### P1-5：E2E 未覆盖真实 operator path

Playwright `feedback-governance-flow.spec.ts` 使用 route interception mock API，验证 UI contract/receipt 渲染，**不验证 PG 突变 `CandidateReady → Promoted`**。W5-06/W5-08 证据对渲染/a11y 强，对治理突变弱。

**建议**：至少一条 real-stack Chromium：fixture CandidateReady → issue permit → activate → assert Promoted + receipt + route generation。

### P1-6：WS stale 策略分裂

| 表面 | 策略 |
|------|------|
| Feedback | `wsStore.status !== 'connected'` 才 15s poll |
| Dashboard | 45s stale + `dashboardWsHealth` |

Connected-but-stale WS 在 Feedback **不触发 recovery**，违反 §7 degraded/recovery bounded polling 精神。
