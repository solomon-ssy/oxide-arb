## 0. 一句话结论

**Implementation Closure（软件合同）大体成立，但不是“生产级最佳实践的完整闭环”。**

相对历史上阻断性的四个 P0（orphan promote、DSR/PBO bypass、双轨 publish、unknown-market 丢 fact），当前代码方向正确且主环已可治理。  
相对 Google CT / champion-challenger / TreeSHAP / 因果命名文献，以及 11.9 §4–§7 自身文字合同，仍存在**实质空洞、控制面缺陷与文档超额宣称**。

`Operational Activation=BLOCKED` **正确**，不计入未闭环。

一句话：

> 主干 DAG + 唯一 serving authority + CandidateReady 人工两步是对的；scheduler 控制面、attribution 生产语义、Drift 再训练策略、Domain Sources 文案，还没到生产级完整闭环。

## 5. 缺陷账本（按严重度）

### 5.1 P0 — 相对 §4 合同的生产语义空洞

#### P0-A — `OutcomeAssociation.execution_rollup_set_hash` 空绑定

**位置**：`crates/quant-pivot-core/src/service/feedback_attribution.rs`（约 L1111–1115）

```rust
let execution_rollup_set_hash = CanonicalDigest::content_hash_typed(
    ASSOCIATION_EXECUTIONS_DOMAIN,
    ASSOCIATION_VERSION,
    &Vec::<ContentHash>::new(),
)?;
```

**合同**：§4 — explanation 与 resolution/**execution rollup** 的带不确定性条件关联。  
**现实**：只绑 resolution payout；execution 字段是空向量的 content hash，外观完整、内容空洞。  
**风险**：WORM artifact 形成“已绑定 execution”的假证据；下游 gate / UI 若展示该 hash 会误导审计。  
**修复方向（破坏式可接受）**：真绑 cohort 内全部 terminal rollup hash；或删除该字段并改写合同 / API / UI，禁止保留空 stub。

#### P0-B — `PolicyCounterfactualOutcome` 生产路径未兑现 barrier / missed return

**位置**：同文件约 L1947–1997

- 生产永远 `AlternativeExitPolicy::LatestExecutableAtOrBeforeHorizon`
- `baseline_realized_return_bps: None` → `gross_return_delta_bps` 恒为 `None`
- `FirstBarrier` 仅存在于类型与单测

**合同**：§4 — alternative exit/**barrier** policy 下的 missed return。  
**现实**：library-true, production-false。  
**修复方向**：生产枚举并封存一组版本化 alternative policies（含 barrier）；强制传入 realized baseline；缺失 baseline 则 fail-closed 或不产出该 artifact。

#### P0-C — “dependency-aware counterfactual” 名不副实

**位置**：`crates/quant-pivot-research/src/attribution/artifacts.rs`

- `DECISION_DEPENDENCY_NODES` = 固定 5 字符串
- `dependency_graph_hash` = 对该列表的 content hash
- 干预多为单特征置零 + score/TopN 重排，非边驱动失效重放

**对照文献**：Causal Shapley / do-calculus 要求因果图或干预传播；当前不是。  
**修复方向**：

1. 诚实改名：`DecisionScoreInterventionReplay` / 删除 “dependency graph” 话术；或  
2. 引入版本化依赖图 + 祖先失效重算，并进 efficiency / identity gate。

### 5.2 P1 — 控制面 / 再训练闭环缺陷

#### P1-A — Pause 不是完整 kill switch（manual 可绕过）

| 路径 | 行为 |
|---|---|
| `claim_due` | `Paused.eq(false)` —— scheduled 遵守 pause |
| `record_governed_trigger` | 只校验 profile / cadence window —— **不检查 `scheduler.paused`** |

**合同**：§3 / §10.2 将 pause 与 cooldown 并列。Cooldown 对 manual 生效；pause 不对。  
**风险**：运维以为 pause = 停止一切反馈开火，实际人手仍可创建 cycle。  
**修复**：manual trigger 与 scheduled claim 共用 pause 不变量；补 CAS 负向测试。

#### P1-B — Lease-loss 破坏“失败原 identity retry”

**位置**：`crates/quant-pivot-core/src/service/feedback_scheduler.rs`（lease 心跳失败 → `return`，不 `settle_retry`）  
**配合**：`feedback_scheduler` repo claim：`retry_at.is_none()` 时用 `cadence_cutoff(now)` 重写 cutoff。

**失败模式**：

1. Claim cutoff `T`，cycle `T` 已 insert，lease 在 settle 前丢失  
2. 无 cooldown / `last_cycle_id` 对应 `T`  
3. 时钟跨 bucket 后 re-claim 跳到 `T+1` 并 settle cooldown  
4. Cycle `T` 仍可由 coordinator 推进 → **双 cycle、cooldown 跳过、identity retry 放弃**

**合同**：§3 “失败使用原 identity retry”。`Err` 路径有；lease-loss 路径无。  
**修复**：lease-loss / settle_success 失败必须 `settle_retry` 并保留原 `next_due_at`；补故障注入矩阵。

#### P1-C — “Auto-Retraining” 实质是 Drift 门控，不是 cadence floor

**位置**：`crates/quant-pivot-research/src/feedback.rs` `drift_gate`

- 阈值超限 → `Advance`（继续 DatasetSeal→Training）  
- 否则 → `NoAction`（`feedback_drift_not_detected` / insufficient evidence）  
- Manual 走同一 gate，**不能 force retrain**

**业界**：成熟 CT = **scheduled floor + drift/perf trigger**（datarekha / Google）。  
**现实**：cadence = 定期检查；只有 drift 超阈才训练。

| 若产品意图 | 判定 |
|---|---|
| Drift-closed loop | 实现可接受，但文档/标题必须改，去掉“按 cadence 自动再训练”的过度承诺 |
| Time-closed retrain loop | **未闭环**——缺 scheduled floor 与 OperatorForced |

**建议破坏式合同**：

```text
RetrainTrigger ::= ScheduledFloor | DriftTriggered | OperatorForced
```

- Floor：每个 cooldown 窗口至少一次完整训练尝试（仍过 quality gate）  
- Drift：阈值超限触发  
- Forced：人工，受 cooldown/CAS/pause，**不受** `NoThresholdExceeded` 拦死  
- 三者共享同一 DAG 后半段与唯一 quality gate

#### P1-D — Attribution `uses` 封存但不被 recipe / training 消费

**位置**：

- 写入：`feedback_governance.rs` `plan_attribution` → `FeedbackAttributionPlanArtifact.uses`  
- 消费：`feedback_dataset.rs` / training 路径 **无** `FeedbackAttributionUse` 读取

**合同**：§4 “cycle N 的 recipe planner 只能消费 prior artifacts”。  
**现实**：

- 有：PIT 防泄漏（同 cycle / 晚 cutoff 拒绝）+ 治理证据清单  
- 无：用前序归因驱动候选 recipe / 特征选择 / 干预策略

**判定**：11.10 并入 11.9 后最大的“看起来闭合、业务未闭合”点——归因偏 **旁路证据生成**，不是 **反馈进训练**。  
**修复**：要么 uses 进入 DatasetSeal / candidate recipe 构造；要么合同改写为 “evaluation evidence inventory”，删除 “recipe planner consumes” 话术。

#### P1-E — `list_available` 无 profile 隔离

**位置**：`crates/quant-pivot-repository/src/postgres/quant/attribution_artifact.rs`

过滤仅：`source_feedback_cycle_id != current`、`source_cutoff < cutoff`、`available_at <= cutoff`。  
跨 research profile 只要时间戳过关即可进入 uses。  
**风险**：多 profile 同库静默污染。  
**修复**：按 `research_profile_id` / policy lineage 强制隔离。

#### P1-F — Domain Sources UI 违反 §7（declared 标为 active）

**位置**：

- `ui/.../domain-sources/modules/domain-source-presentation.ts`：`crypto`/`weather` = 行数  
- `page.json`：`activeCursors` / `activeFeeds`  
- `domain-sources/index.vue`：Statistic 绑定上述计数

**合同**：§7 — 分离 declared / observed / stale / blocked / unobserved；**不把 declared count 标为 active**。  
**判定**：明确产品缺陷，非吹毛求疵。  
**修复**：摘要分桶与文案对齐；`live` 才可称 active；blocked/unobserved 独立计数。

#### P1-G — Rollback 深链未闭环 + receipt 不完整

| 项 | 现状 |
|---|---|
| Receipt | session-local；缺 audit/outbox/policy activation 等 ID 的完整展示 |
| Rollback | `RouterLink` → `/system/config/model_routing`，无 generation/revision query |

**合同**：§7 — typed receipt + actor lineage + **现有 Model Routing rollback 深链**。  
**判定**：旅程可走通，闭环未封。  
**修复**：receipt 持久化或可重取；rollback 深链携带目标 generation / revision；E2E 断言落地。

#### P1-H — Operator reason grammar 不一致 + activate E2E 证据过强

（与既有 remediation 复审一致，本轮复核仍 OPEN）

- trigger/cancel：机器语法  
- permit/activate/scheduler：偏自由 note  
- 有 mock 旅程 / a11y；**缺** Chromium 真实 issue→activate 突变 E2E

**影响**：Implementation Closure 证据不得被解读为“浏览器证明了 promote 路径”。

### 8.1 认同的决策

- Implementation Closure ≠ Operational Activation

## 10. 建议 Remediation 顺序（破坏式可接受）

> 目标：把“软件合同可接受”推进到“生产级完整闭环”。不追求最小 diff。

### Wave R1 — 控制面正确性（先于任何激活）

1. Pause 阻挡 manual trigger；负向契约测试  
2. Lease-loss / settle_success 失败 → `settle_retry` 保留原 cutoff；故障注入  
3. 文档化或实现 cadence catch-up 策略（当前 skip historical buckets）

### Wave R2 — Attribution 生产诚实度

1. OutcomeAssociation 真绑 rollup set，或删除字段并全链路改合同  
2. Policy CF 生产跑版本化 alternative set + realized baseline；缺失 fail-closed  
3. Decision CF：真依赖图 **或** 破坏式改名去 “dependency graph”  
4. 合同与代码对 GBDT-only TreeSHAP 对齐；或补 RF/ExtraTrees portable preimage

### Wave R3 — 归因进训练 / 再训练策略

1. `FeedbackAttributionUse` 进入 DatasetSeal / candidate recipe，或删除 “recipe consumes” 话术  
2. `list_available` profile 隔离  
3. 引入 `ScheduledFloor | DriftTriggered | OperatorForced`；强制通道不受 `NoThresholdExceeded` 拦死（仍受 pause/cooldown/CAS/quality gate）

### Wave R4 — Weather / Observability

1. Regex compile fail-closed；恢复可观测 parser-debt 终态（新枚举名可，禁止永久折进 InsufficientEvidence）  
2. Sea Ice 15%：代码强制或合同改为 “product-as-published”  
3. §8 指标配 alert + runbook（有 metrics ≠ 有 alerting）

### Wave R5 — UI/UX 闭环

1. Domain Sources：declared ≠ active；分桶对齐 §7  
2. Receipt 可重取 + 完整 ID；rollback 深链带 generation/revision  
3. 复用 `QualityGateScorecard` + i18n gate 名  
4. Action / Domain Sources 可见 Alert+retry  
5. Chromium：CandidateReady fixture → issue permit → activate → Promoted + receipt + route generation  
6. permit/activate/scheduler 与 trigger/cancel 统一 reason/note 合同  
7. Feedback ↔ Dashboard 共享 WS stale/visibility 策略  
8. zh-CN 弱化因果负载（“解释 / 关联 / 反事实重放”）

### Wave R6 — 文档与证据收敛

1. 收缩 11.9 §4–§7 / §12 超额宣称，使合同 = current bytes  
2. ImpClosure 证据明确写出：activate E2E 仍 OPEN（直到 R5 补齐）  
3. 禁止继承本轮之外的历史 closure 流水
