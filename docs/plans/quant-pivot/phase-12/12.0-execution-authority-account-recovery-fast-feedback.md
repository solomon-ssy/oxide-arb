## 1. 审计结论与固定决策

### 1.1 ReportOnly 与 runtime mode

`QuantRuntimeMode` 同时承担了五个彼此正交的职责：报告是否可读、intent 授权来源、自动提交许可、退出自动化和 settlement write policy。现有 kill switch、per-recommendation execution eligibility、intent approval、trade-policy authority 和独立 settlement policy 已经分别拥有这些事实，因此三态 runtime mode 是重复控制轴。

Phase 12 删除整个 mode 轴：

- 报告不再冻结 runtime mode，且在 entry halt/recovery 状态下仍可生成。
- recommendation 只冻结最大执行权限 `ExecutionAuthorityCeiling`。
- runtime 只冻结当前 `EntryAuthorizationPolicy`。
- intent 冻结不可变 `AuthorizationEvidence`。
- kill switch 单独控制新入场、正常退出和 emergency exit。
- settlement write policy 继续独立治理。

默认 `EntryAuthorizationPolicy::OperatorApprovalRequired`。用户不创建或不批准 intent 即不会下单，因此无需全局 `ReportOnly` 才能安全观察报告。

### 1.2 Polymarket UI 与账户单写者

Polymarket Data API 可按 wallet 读取 trades/activity，但没有完整的未成交订单生命周期；authenticated User Channel 按 API credential 过滤。V2 `OrderFilled` 链上事件提供 order hash、maker、taker、side、token、amount、fee、builder 和 metadata，可在不依赖 UI credential 的前提下精确识别 finalized funder execution。

固定策略：

- 正常运行只允许本系统向策略账户写入订单。
- 未与系统 order 或已封存 recovery incident 绑定的 finalized account execution 是 `UnknownExternal`。
- `UnknownExternal` 原子创建/复用 `AccountRecoveryIncident`，并把 kill switch 置为 latched `ExitOnly`。
- 不创建 `ManualExecutionOutcome`，不事后伪造 `OrderIntent`。
- 系统停机时允许严格 break-glass UI exit，但恢复必须经过 user pause、finalized replay、lot allocation、账户精确对账和 governed unpause。

### 1.3 MTM 与 terminal outcome

现有数据面已经拥有 MFE/MAE、liquidity、policy net return、full-L2 replay、fee schedule 和真实 attempt trajectory。缺口不是另一个简化标签器，而是 recommendation 在 profile horizon 上的独立、WORM、可成交经济结果。

固定策略：

- `token_payout_ratio` 继续是 Buy 模型唯一终局监督目标。
- `RecommendationEconomicOutcome` 是 PolicyEvaluation/operational health fact，不进入 ModelLearning、calibration 或 promotion label count。
- 必须复用 `PolicyReplayKernel` 和既有 book/fee execution semantics。
- horizon mark 必须是 full-depth executable sell walk；禁止 mid、last trade、Data API mark 或 top-of-book fallback。

### 1.4 Sports

Sports 不是 Phase 12 的实施范围。官方 Sports WebSocket 明确可能延迟、错误或漏事件，不足以支撑执行级 alpha。只有批准带实时 SLA 和历史回放的数据源后，才允许单独设计 `DomainFamily::Sports`/`BuyModelRoute::Sports`；禁止在当前 Pooled 路径加入半实现 Sports 类型或公共源降级。

## 2. 唯一领域模型

### 2.1 Entry authorization

```rust
pub enum EntryAuthorizationPolicy {
    OperatorApprovalRequired,
    PolicyAutomatic,
}

pub enum ExecutionAuthorityCeiling {
    AnalysisOnly,
    OperatorApproval,
    PolicyAutomatic,
}

pub enum AuthorizationKind {
    OperatorApproval,
    ActivePolicy,
}

pub enum AuthorizationEvidence {
    OperatorApproval {
        user_id: UserId,
        reason: String,
        authorized_at: DateTime<Utc>,
    },
    ActivePolicy {
        policy_id: String,
        policy_hash: ContentHash,
        authorized_at: DateTime<Utc>,
    },
}
```

`EntryAuthorizationPolicy` 是 runtime state；`ExecutionAuthorityCeiling` 是 recommendation frozen capability；`AuthorizationEvidence` 是 intent immutable grant。三者不得合并为一个“mode”。

`ExecutionEligibility` 唯一形状：

```rust
pub struct ExecutionEligibility {
    pub ceiling: ExecutionAuthorityCeiling,
    pub blockers: Vec<IneligibilityReason>,
    pub policy_binding: Option<ExecutionPolicyBinding>,
}
```

不保存 `approval_required`、`eligible_modes`、`requires_approval` 或 `auto_execution_allowed` 等派生布尔量。

### 2.2 OrderIntent FSM

唯一状态集：

```text
PendingAuthorization
Authorized
AdmissionPending
AdmissionRejected
Submitted
PartiallyFilled
Filled
AuthorizationRejected
Cancelled
Failed
Expired
Invalidated
```

规则：

- Operator policy 下 create 产生 `PendingAuthorization`，授权后成为 `Authorized`。
- PolicyAutomatic 下只有 active policy、recommendation ceiling、economic health 和 preflight 全部通过时，才能原子创建 `Authorized` intent。
- `authorization_kind` 在创建时确定；`authorization_evidence` 只在 `Authorized` 及其后继状态存在。
- 删除 `ApprovalStatus`、`Draft`、`Approved`、`ApprovedByPolicy` 和单 variant `OrderIntentKind::Buy`。
- capital reservation、authorization、condition arm 和 dispatch wake 继续遵循现有事务边界。

### 2.3 Runtime controls

`RuntimeControlSnapshot` 只保存：

- `entry_authorization_policy`
- `settlement_write_policy`
- `kill_switch_state`
- kill-switch latch/ack
- revision、actor、reason、changed_at

切到 `PolicyAutomatic` 是 capability upgrade，必须执行 `EntryAuthorizationPreflight`；回到 operator approval 是 fail-safe downgrade，不需要 readiness preflight，但仍需 CAS、RBAC 和 WORM operation log。

Fresh route bootstrap 必须在 `ExitOnly` 且账户 recovery seal healthy 时进行，不再依赖 `ReportOnly`。

### 2.4 Canonical Polymarket order contract

`PolymarketOrderRules` 是 report/backtest/admission/entry/exit/reconciliation 与 SDK adapter
共享的唯一订单数学 owner。规则必须来自 decision-time `clob_market_info_version`，并冻结
`market_id/token_id/tick_size/minimum_order_size/neg_risk/payload_hash`；禁止从当前配置、book
top 或 SDK mutable cache 推测。

- 支持的六种 tick 均按 typed `TickSize` 校验 price scale、tick alignment 和
  `[tick, 1-tick]` 边界。
- 用户 amount 只有 BUY `PrincipalUsd` 或 BUY/SELL `Shares` 两种语义；SELL USD amount
  非法。principal/shares 先向零 floor 到两位，counter amount 按 tick 对应的 3–6 位 scale
  floor，最终 maker/taker wire amount 精确投影为 `10^6` integer。
- aggressive BUY limit 向下取可成交 tick；SELL hard minimum 向上取 tick；任何 floor 后为零、
  低于 venue minimum、越界或非 canonical precision 都 fail closed。
- admission、prepared evidence 与 execution WAL 必须逐字段相等：market、token、side、order
  type、GTD expiration、limit price、requested shares；reconciliation 必须重新运行同一 kernel，
  不接受近似相等或事后规范化。

签名前 final hop 必须重新读取同一 token 的 `/book` 与 condition 的 `/clob-markets/{id}`，
核对上述 identity 和 canonical payload hash；同时读取真实 V2 funding：BUY 需要 collateral
balance/allowance 覆盖 principal + projected fee，SELL 需要 conditional-token balance/allowance
覆盖 shares。raw `uint256` 只按 USDC/CTF 固定 `10^6` scale 转换，spender 必须是当前
standard/NegRisk exchange；缺失或不足只返回 typed funding denial，系统绝不自动 approve。

Polymarket SDK 的 tick/NegRisk cache 是 mutable process state，因此从 seed rule、build unsigned、
validate payload 到 chain-bound signer 完成签名必须由同一 async mutex 串行化；锁在网络 POST
前释放。POST timeout/ambiguous result 进入 durable reconciliation，不得重签生成第二订单。

### 2.5 Crypto continuity and durability

每个 Crypto source/instrument 的事实显式绑定 `gap_generation + source_sequence + event_time +
report_hash`。断线、gap 或 recovery 开始时先推进 generation，再接受该代事实；同一 continuity
identity 出现不同 hash 是 equivocation，不得 last-write-wins。

写入链路使用有界 ordered receipt queue：ClickHouse durable writer ACK 队首后，才允许推进
source checkpoint/frontier 并释放下一条 receipt。ACK timeout、重复消费、队首丢失、缺 generation、
sequence discontinuity、batch 内重复 identity 或 hash 冲突都使对应 source session 失效并
fail closed；shutdown 只按相同 ACK 顺序 drain，不把已 enqueue 当成已持久化。

### 2.6 Concurrent terminal ownership

- report schedule 先读取 activation，再按其 immutable snapshot id 读取配置，不能把两个独立的
  current reads 误当成原子快照。仅在 reconcile/materialize/claim 的已知 CAS 调用点，错误的
  entity、expected id 和完整 reason 全部精确匹配时，才作为正常 configuration race 记录 INFO
  并等待下一轮；缺失配置、错误 id/reason、执行或 health 路径错误仍为 ERROR。
- report fact announcement 只能 claim `Published` report；revoke/expire 等 terminal transition
  原子清除 claim。若 transition 在 delivery ACK 前胜出，ACK 返回 typed `ClaimLost`，worker 记录
  已处理的 terminal race，不重试或报 invariant。
- settlement discovery 的每个持久化 operation 只对 PostgreSQL `40001`/`40P01` 做最多四次
  bounded retry，退避为 10/20/40ms 加 0–50% jitter。并发 winner 只有在 durable identity 与
  digest 精确一致且 revision 更新时可接受；stale identity/digest 是 typed conflict/defer，row
  自身不一致仍是 invariant violation。

### 2.7 Process-owned I/O and shutdown

应用 lifecycle 是 SIGINT/SIGTERM 的唯一 owner；Actix 自有 signal handling 必须关闭。
HTTP request、streaming response body 与 detached WebSocket session 保留 Actix `LocalSet`
执行位置，但每次 poll 和 Drop 都进入 process Tokio runtime。共享 PostgreSQL/Redis 等 I/O
与 SQLx connection-return/maintenance task 不得绑定先于 core drain 销毁的 worker reactor。

HTTP shutdown 必须持续 poll `Server`，同时等待 graceful-stop ACK，不能先 drop command
receiver 再把 ACK channel 关闭当成成功。HTTP request grace 使用 `WsIngress` stage budget
的一半，剩余预算用于 worker cancellation、resource Drop 与 stop ACK。策略 bundle reconciler
由统一 TaskRegistry 的 `HealthMonitor` stage 取消并 join，构成不再 publish 的 barrier；所有
业务、研究、持久化与 fanout consumer 排空后，composition root 在 `DbClose` budget 内显式
await PostgreSQL pool close，再关闭 Redis。关闭失败或超时必须保留错误，不得以进程退出掩盖。

真实 binary 验收使用 owned disposable PostgreSQL 的 30 秒 connection lifetime，显式证明
连接替换与 HTTP readiness 并存，再以 SIGINT 验证统一 drain。Browser fixture 的账户、report、
intent、lot、venue mark 与 equity 必须一致；holding value 不得混作 cash，缺 mark 不得补零。

## 3. 账户成交与库存真相

### 3.1 三个不同的事实平面

1. `quant_exchange_event`：保留。Accepted V2 raw event，链上事实源。
2. `quant_market_execution` / `quant_execution_participant`：保留。全市场研究事实；不承担账户头寸权威。
3. `quant_account_chain_execution`：新增。某 execution account/funder 的 finalized economic execution；是账户 chain settlement 与 exact fee 权威。

`quant_execution_fill` 替换为 `quant_clob_trade_observation`：它只表示 authenticated CLOB trade lifecycle 和低延迟状态，不再自称最终 chain execution。

### 3.2 Account chain execution

`quant_account_chain_execution` 至少保存：

- `account_chain_execution_id`（由 account + exchange event content address）
- `execution_account_id`
- `exchange_event_id`
- chain/contract/version/block/transaction/log/order hash
- token/market
- account participant role
- role-adjusted account side
- shares、price、principal、exact fee
- builder、metadata
- effective/observed/available time
- source event hash、outcome hash、schema version

Maker 使用逐 maker `OrderFilled`；Taker 使用 match group 的 aggregate taker event，避免把 maker side/fee 错写给 taker。自成交必须保留两条经济 leg 或产生 typed quarantine，不能静默净额。

### 3.3 Association

Chain fact WORM，不因后续归因而更新。`quant_account_execution_association` append-only 绑定：

```text
SystemOrder(execution_order_id, order_intent_id)
AccountRecoveryIncident(account_recovery_incident_id)
UnknownExternal
```

同一 account chain execution 只能有一个 current association；冲突进入 quarantine。

### 3.4 Fee owner

- Prepared projected fee：保留在 prepared order/economic evidence。
- CLOB provisional fee/rate：保留在 `quant_clob_trade_observation`。
- Final exact fee：只来自 `quant_account_chain_execution`。
- 删除 `quant_execution_fee_measurement` 和 `FeeSettlementService`；所有 outcome/PnL/incentive consumer 迁移到上述三个明确阶段。

### 3.5 Strategy position lot

`quant_position` 重建为 `quant_strategy_position_lot`；`PositionInfo` 重命名 `StrategyPositionLot`，venue account aggregate `PositionSnapshot` 重命名 `VenuePositionSnapshot`。

Lot origin：

```text
SystemIntent(order_intent_id)
AccountRecoveryIncident(account_recovery_incident_id)
OpeningInventory(opening_inventory_hash)
```

外部部分卖出涉及多个 lot 时，恢复必须要求 operator 明确分配；禁止 FIFO、平均价或时间窗猜测。全量卖出可由 share conservation 唯一分配。

## 4. 单写者与 break-glass

### 4.1 Unknown external execution

Finalized account execution 无 system order/recovery binding 时：

1. 原子创建或复用 `AccountRecoveryIncident`。
2. association 记为 `UnknownExternal`。
3. kill switch 置为 latched `ExitOnly`。
4. 停止新 intent 创建/提交；已有受治理退出和 settlement 保留。
5. 发出高优先级 alert 和 metric。

### 4.2 Recovery incident FSM

```text
Open -> Reconciling -> Sealed
                    -> Rejected
```

保存 outage window、trigger、actor/reason、external executions、lot allocations、before/after account snapshot、open-order evidence、pause/unpause facts、recovery manifest/hash。

### 4.3 Strict break-glass contract

- UI 只允许立即成交型 exit；禁止 GTC/GTD 或任何可能 resting 的订单。
- 操作者完成后在 UI 撤销全部订单。
- 对配置中的每个当前 V2 Exchange，以真实 funder 调用 `pauseUser()`。
- 动态读取 `userPauseBlockInterval`，等待 pause effective block 和项目确认深度；禁止硬编码 100 blocks。
- Proxy/Safe/Deposit Wallet 复用 wallet-topology/relayer owner；验证 `isUserPaused(funder)`。
- restart 自动进入 recovery-only：追平 history/pause events、读取 managed CLOB orders/trades、投影 account executions、精确对账 collateral/positions/reservations/lots/settlement。
- seal 前禁止 `unpauseUser()`；unpause 后再次等待 finality 才能恢复 operator entry policy。
- 使用过 resting UI order、无法证明零挂单、lot allocation 不唯一或账户不收敛时保持 paused；唯一恢复出口是 clean funder + fresh boot。

## 5. Recommendation economic outcome

### 5.1 WORM contract

`quant_recommendation_economic_outcome` 以 `recommendation_id` 为唯一业务键，冻结：

- profile/policy/model/report/recommendation identity
- decision/horizon/terminal/available timeline
- cash tier、entry/exit policy hashes
- entry/exit fill economics、fees、rebate evidence、latency
- full-L2/fee/passive-trade coverage
- source slice/checkpoint hashes
- typed state、outcome hash、schema version

Typed state：

```text
EntryNotTriggered
EntryUnfilled
PolicyExited
HorizonLiquidated
ResolvedBeforeHorizon
Censored(typed_reason)
```

### 5.2 Computation owner

- 只调用现有 `PolicyReplayKernel`。
- 使用 frozen recommendation 的实际 cash tier 和 trade plan。
- horizon open position 用 full bid ladder 执行 forced FAK sell walk。
- 缺 L2、sequence continuity、fee、depth 或 PIT availability 时返回 typed censor，不写零。
- market 先结算时使用 canonical payout，但 resolution outcome 仍是独立 WORM truth。
- horizon 是 frozen profile 的不可变身份，不是已终局市场的强制等待下界。已提交、hash-valid 且
  PIT 可见的 canonical resolution projection 可以提前触发 economic claim；它只提供调度锚点，
  entry、fee、passive coverage、exit 与 payout 仍由同一个 `PolicyReplayKernel` 验证。
- 首次 claim 冻结独立 `replay_until`、resolution commitment 与 source lateness cutoff；提前终局
  时点必须满足 frozen `DecisionBoundary` 的 knowledge lag。不得生成未来 replay tick、把 horizon
  改短、滑动重试 deadline，或在 source deadline 前把缺失数据永久写成 censor。
- economic outcome 与 task completion 在同一事务提交，并核对 claim owner、attempt generation
  和未过期 lease。过期 claimant 不得写 WORM；最终 availability 由数据库赋时并参与封存 hash。
- payout fill/terminal 使用 replay 真正消费可见 resolution 的时点，不回填成早于入场的 raw
  observed time；canonical resolution 的原始 event/observation 时间保留在独立 source truth。
- 复用进程级 `ComputeExecutor`，source load 前取得 4 GiB memory lease，hash/reconstruction/replay
  进入既有独占 offline job/CPU owner；上限为 10000 decision points 与 2000000 ladder cells。
  每次只即时 claim 一条，lookup/replay 的共享 async wait budget 为 30 秒、持久 lease 为 60 秒。
  取消后不发布结果；纯 CPU 的 cancellation 是协作式，真实工作结束前不得释放 CPU/memory
  lease，不得宣称 Tokio deadline 能抢占同步代码。
- memory→job→CPU 必须先以不排队方式完整准入；容量不足返回显式 `CapacityDeferred`，durable
  retry 后停止本 pass 继续领取任务。容量争用不是源数据缺失，即使 source cutoff 已过也不得
  写 censor 或移动截止时间；真正准入后的 replay timeout 仍是错误，严格日志门禁不作豁免。
- 校准／backtest 已持有的 memory lease 与 job cancellation 必须贯穿 model-preimage graph、
  Dataset 和 Source Slice 验证；内层不得再次申请同一全量配额或创建失联 cancellation token。
  始终保留完整对象验证，不以降为 runtime-only 检查来规避资源所有权错误。
- N→N+1 验收必须等待 resolution 与 economic 两个真实 WORM 平面后才冻结 cohort cutoff；
  `PolicyEvaluation Eligible` 本身不证明非 censored 经济闭环，还必须核对合法终态、coverage、
  return 与各自 evidence hash。

禁止：

- 第二套 MTM simulator。
- mid/last trade/Data API mark/top-of-book fallback。
- 把 `RecommendationEconomicOutcome` 转成 `ModelTrainingTarget`。
- 复制 `ExecutionTrajectoryArtifact` 或 `PolicyCounterfactualOutcome` 的 actual-attempt 语义。

### 5.3 Route economic health

`quant_route_economic_health` 状态：

```text
InsufficientEvidence
Healthy
Degraded
DataIncomplete
```

统计合同：

- 复用 profile 的 minimum observations、coverage、minimum effect、confidence、block length/repetitions/seed。
- overlapping intervals 使用 average-uniqueness weight。
- resampling 以 market/event cluster，不能把连续 recommendation 当独立样本。
- `InsufficientEvidence` 只允许 operator-authorized execution。
- `Healthy` 允许达到 recommendation ceiling 的 authority。
- `Degraded` 或持续 `DataIncomplete` 阻断该 Route 全部新入场，直到新 policy/evidence 治理解除。
- Economic health 只能阻断/降权，不能授予 model promotion 或 automatic authority。

### 5.4 Feedback boundary

- PolicyEvaluation 消费 economic outcome。
- ModelLearning/ModelScoreLearning 的 mature/new label count 不消费 MTM。
- Buy training/calibration 继续只读 `token_payout_ratio`。
- 真实 attempt 的 planned-vs-actual latency/slippage/fill/fee/return 继续复用现有 `ExecutionTrajectoryArtifact` 和 `PolicyCounterfactualOutcome`。

## 8. 失败语义

- 任何来源缺失、identity 冲突、chain finality 不足、fee 不可验证、账户不收敛、ghost-order 不可排除、economic coverage 不足都 fail closed。
- Absence 不编码成 zero/unfilled。
- Operator approval 不得绕过 recommendation blocker、kill switch、account recovery 或 degraded economic health。
- `PolicyAutomatic` upgrade 不得绕过 preflight、route ceiling 或 operational activation。
- 外部成交不自动归因 recommendation。

## 9. 验收

必须通过：

- runtime-mode old symbol/type/table/route/config/UI/active-doc absence scan。
- intent authorization FSM property/concurrency tests。
- maker/taker/aggregate/self-trade/exact-fee golden tests。
- abrupt stop、unknown execution、pause delay、unpause race、ghost-order blocker fault matrix。
- recommendation economic outcome 全状态、PIT/hash、crash/retry tests。
- MTM 不增加 terminal mature-label count 的负例。
- fresh PostgreSQL/ClickHouse schema fixed point、Rust↔TypeScript schema sync、production Browser E2E。
- `cargo xtask production-stack feedback-closure --runs 1 --retain-artifacts` 只能使用 owned
  disposable PostgreSQL/ClickHouse/Redis 与 loopback upstream/rejector。其 typed manifest 必须同时证明
  `evidence_scope=owned_disposable_only`、`production_composed_binary=true`、
  `outbound_write_endpoints=owned_loopback_rejectors`、runtime control before/after 完全相等、
  `EntryAuthorizationPolicy=OperatorApprovalRequired`、`SettlementWritePolicy=Disabled`、
  `execution_authority_unchanged=true`、money-path counts before/after 完全相等、
  `real_venue_order_write_count=0`、`real_chain_write_count=0`、`real_capital_write_count=0`、
  `relayer_request_count=0` 且 `operational_activation_claimed=false`。
- workspace fmt/clippy/architecture/tests 与 UI lint/typecheck/test/build。
- 两轮 fresh-stack UI 验收同时要求 Playwright exit 0 与 backend nonce-bound terminal success。
  每轮使用唯一 completion 路径与 nonce；backend 启动前写 Pending，只有真实 binary drain、
  strict runtime-log validation 和所有 owned cleanup 完成后才能写 Succeeded。Missing、Pending、
  wrong nonce 或 Failed 一律阻断下一轮；不得把 Playwright 忽略的 webServer teardown failure
  当成成功。普通验证禁止更新 golden，最后比较 51 个场景的 canonical screenshot hash。

Implementation Closure 不宣称 `PolicyAutomatic` 已激活，也不包含真实 venue order、chain
approval/redeem、relayer request 或 controlled canary。这些资金动作属于独立 Operational
Activation，必须对 exact account/route/action/amount/deployment digest 取得操作者授权，并要求
account recovery seal healthy、无 unknown external execution、terminal model/policy gates、MTM coverage、
Healthy Route 和独立 governed activation。
