## 1. 产品边界与信息架构

Config Console 的单一入口是 `/system/config`。它只承载两类相互隔离的 authority：

1. 六类 governed policy resource：可创建 immutable draft，依次 validate、approve、preflight、CAS activate 或显式 rollback。
2. restart-bound deployment/lifecycle evidence：只读展示运行实例、endpoint、secret readiness、resource budget 与 lifecycle 状态；Web 不修改 deploy TOML，也不执行 reset。

页面结构：

| Route | 业务职责 | Mutation |
|---|---|---|
| `/system/config` | 六类资源的 active revision、candidate、generation、健康与最近活动总览 | 无 |
| `/system/config/:resource` | 单资源 typed workspace、revision lineage、diff、validate/approve/activate/rollback | governed |
| `/system/config/deployment` | environment、instance/deployment identity、endpoint、secret readiness、resource budget | 无 |
| `/system/config/activity` | 跨资源 append-only governance timeline | 无 |
| `/system/config/lifecycle` | readiness、evidence、schema/policy fingerprint 与 production-seal confirmation | 仅 seal |

六类 resource 固定为 `recommendation_policy`、`execution_risk_policy`、`model_routing`、
`report_schedule`、`operational_control`、`execution_authorization`。资源之间独立 revision，activation
提交新的完整 bundle generation；不存在把六类文档整体覆盖的全局 version。

## 2. API 与治理状态机

所有路径位于 `/api/config`，API version 由 `Accept-Api-Version: v1` header 声明：

| Method / path | 语义 |
|---|---|
| `GET /resources` | 资源总览与当前 generation |
| `GET /{kind}/current` | active resource 与治理 metadata |
| `GET /{kind}/schema` | 该 resource 的 typed field schema |
| `GET /{kind}/revisions?limit=` | bounded revision history |
| `POST /{kind}/drafts` | 基于 expected generation 创建 immutable draft |
| `POST /{kind}/drafts/{id}/validate` | typed validation 与 dependency evidence |
| `POST /{kind}/drafts/{id}/approve` | exact revision/hash approval |
| `POST /{kind}/drafts/{id}/activate` | consumer preflight 后 CAS activation |
| `POST /{kind}/revisions/{id}/rollback` | 以历史 revision 为目标重新走治理链 |
| `GET /activity` | bounded governance activity |
| `GET /snapshot-options` | 可绑定的完整 policy snapshot |
| `GET /deployment` | secret-redacted deployment projection |
| `GET /lifecycle` | lifecycle readiness/evidence projection |
| `POST /lifecycle/seal-production` | 不可逆 production seal |
| `POST /schedule-preview` | report cadence 的纯计算预览 |

mutating request 必须同时携带 server-side RBAC、`X-Acting-Role`、reason 与 idempotency/CAS
材料。状态转换的判断以数据库事务中的 revision、approval、active bundle generation 与 evidence 为准；
UI capability 只决定呈现，不能代替服务端授权。409 stale generation 必须保留当前 active 状态并向用户
展示冲突，不自动重放或覆盖。

## 3. Resource workspace

`resource.vue` 同时呈现 active document、editable draft、immutable revision history 和 exact diff。
编辑体验遵循以下规则：

- 字段由后端 `PolicyResourceSchemaView` 描述，前端 `policy-schema.ts` 只做 widget mapping 和本地即时反馈，不复制业务 validator。
- Decimal/money wire value 始终是 string；model routing 使用 Published artifact picker，不接收自由文本 ID。
- report schedule 使用结构化 cadence editor，并调用 `/schedule-preview` 展示同源的 next-fire times。
- operational control 以明确状态转换表达 report pause / execution halt；恢复同样是 governed action。
- execution authorization 明确 `report_only`、`semi_auto`、`auto_execution` 的 canary/budget 约束；`report_only` 不显示为模拟交易。
- validation error 同时进入 error summary 与字段关联提示；summary 获取焦点，修正后焦点回到原操作上下文。
- dirty draft 不持久化，离页必须确认；成功 mutation 后只以服务端响应和重新查询结果更新页面。

rollback 不是指针瞬移：选择历史 revision 后重新生成候选，重新 validate、approve、preflight，并以新的
idempotency key 与 expected generation 激活。`production_frozen` 或缺少 mutation permission 时，所有写入
affordance 都必须消失，服务端仍独立拒绝请求。

## 4. Deployment secret 与数据库身份

Deploy secret 在 TOML 中是明文 string，反序列化后由 zeroizing、non-serializable、redacted-debug
`SecretText` 持有。local-development 的真实值只写 gitignored `quant-pivot.local.toml`；部署环境使用
权限 `0600`、不进入版本控制的 deploy TOML。secret 不通过环境变量、命令行、Config API 或 UI 返回。

PostgreSQL 与 ClickHouse 各自只配置一组 `user + password`，由 runtime、schema CLI 与 Fresh Boot
复用。应用启动只执行 verify；migration/reset/seal 必须显式触发并持有 canonical lifecycle lease。
Deployment 页面只展示每个 secret 的语义名称和 `available/missing/invalid` readiness，不展示来源、
值、长度、文件名或路径。

一次性 bootstrap admin password 是 CLI bootstrap input，不属于 Deploy Config；它仍通过权限受限的
`QUANT_PIVOT_BOOTSTRAP__ADMIN_PASSWORD_FILE` 注入，schema finalize 后应用 runtime 不再读取。

## 5. Lifecycle 与 destructive boundary

Lifecycle 页面是 readiness/evidence 控制面，不是 Fresh Boot 面板：

- Fresh Boot/reset 仅存在于 CLI，Web 不提供 destructive button 或 API。
- preproduction 页面可展示 seal 前置条件；本地验收不得真正 seal。
- seal confirmation 必须展示不可逆语义、目标 lifecycle hash 与缺失 evidence，支持键盘取消和焦点恢复。
- production seal 在 canonical lease 下重新读取 live PostgreSQL/ClickHouse fingerprints、active bundle、build identity 与 WORM evidence；任一漂移都拒绝。
- frozen projection 只读，所有 governed mutation 由 UI 与后端双重拒绝。

## 6. 可执行验收矩阵

Config E2E 不是字符串 manifest，而是 `config-governance.spec.ts` 中的 24 个独立 Playwright test：

- `CFG-01..22`：overview、typed edit、validation/error focus、review/diff、approval、preflight、CAS activation、双 browser context stale conflict、rollback、model routing、schedule preview、operational control、deployment redaction、lifecycle/seal confirmation、frozen、真实 viewer RBAC、transient recovery、execution authorization。
- `X-01`：所有主页面在 1024px viewport 无水平 overflow。
- `X-02`：`prefers-reduced-motion` 下移除入场动画与长 transition。

风险矩阵覆盖桌面明暗主题、关键治理移动端、1024 overflow、高密度 1280、axe、键盘、错误聚焦与
焦点恢复。Linux Chromium snapshot 是唯一基线；CI 分别以 fresh backend 执行 Config governance 和
protected flow，避免前者真实 activation 污染后者的 frozen artifact 前置条件。

通过与否只能引用本轮 Execution Ledger 中记录的命令、时间和 evidence hash；设计文档本身不宣称
当前工作树或远端 CI 已通过。

## 7. 删除与永久非目标

以下内容属于死设计，禁止重新引入：

- `/runtime-config` 页面、`/api/runtime-config/*` route、全局 config version 或 dotted-path patch；
- `runtime-config-editor.vue`、通用递归 JSON/schema editor、BorderBeam section 与浏览器 localStorage section 状态；
- UI 拼装 deploy TOML、secret value/source/path 展示、systemd credential reference；
- deploy drift API、Web reset、Web secret editor、自动 activate、silent CAS retry；
- `DeploySecret`、`SystemdCredentialRef`、runtime/migration 双 identity 或兼容 parser/re-export。

新的 Config 能力必须先证明真实 consumer、server-side validation、RBAC、事务边界、失败恢复和可执行
验收场景；不为假设中的未来 operator 扩展通用 schema DSL。
