# 05.4 — Entry Execution & Venue Submission

> 父：[`README.md`](README.md) · 概念规格：[`../05-execution-risk-and-governance.md`](../05-execution-risk-and-governance.md) §5/§16.4/§17、
> [`../09-account-capital-position-reconciliation.md`](../09-account-capital-position-reconciliation.md) §4
>
> 闭环定位：**真金白银下单闭环**。把 `Approved`/`ApprovedByPolicy` intent 经 admission（05.3）`allow`
> 后建 `quant_execution_order`、用私钥签名提交到 Polymarket CLOB、记录结果、推进 capital FSM
> （locked → spent）、写 `quant_position` 账本、并把订单交给 05.5 对账。**这是整个系统第一次真实
> 动钱**，每一步 fail-closed、可恢复、可审计。

## 1. 目标与闭环定位

1. **core `PolymarketOrderClient` façade**（封装 `quant-pivot-api::ClobClient` 的 `place_order` /
   `cancel_order`），把 venue 下单能力首次接入生产路径（当前仅测试调用，
   [`api/src/clob/mod.rs`](../../../crates/quant-pivot-api/src/clob/mod.rs) §198）。
2. **`ExecutionBundle`**：暴露 order client + dispatcher 到 `AppContext`（替换空壳
   `ExecutionIntentBundle`，[`bundles/future.rs`](../../../crates/quant-pivot-core/src/app/bundles/future.rs) §98–99）。
3. **`ExecutionDispatcher.submit_if_admitted`**（父文档 §16.4）：行锁取 intent → 校验可提交 → 建
   admission input → evaluate → `allow` 才建单 → capital `locked` → 签名提交 → 记录结果 → 写
   position 账本（fill）→ enqueue 对账。
4. **entry 生命周期**（父文档 §5.2）：推进唯一的 `ExecutionOrderState`；`Ambiguous` 入对账不计失败。
5. **order type 策略**（父文档 §5.1）：默认 limit（GTC/GTD），FOK 仅当 recommendation 显式要求即时
   流动性，cancel-on-timeout（GTD）。
6. **capital FSM**：`locked`（提交）→ `spent`（fill）/ `released`（cancel/fail）/ `impaired`（恢复失败）。
7. **metrics**：`quant_execution_orders_submitted_total` / `quant_execution_fills_total` /
   `quant_execution_breaker_trips_total{dimension}`。
8. **`ExecutionBreaker`（§6.5）**：venue 维度自动熔断器——观测提交/撤单结果，瞬态退化驱动 admission
   `#18` defer、持续失败自动 trip kill-switch 到 `execution_halted`（latch + ack）。承载 admission 之外
   的跨决策累计安全态（recon / 日内亏损维度在 05.5 / 05.6 接入同一 breaker）。

本子phase完成后，05.5 对账可消费 `Submitted`/`Ambiguous` 订单，05.6 exit monitor 可消费 `Filled`
position。

## 4. order type 策略（父文档 §5.1）

| 场景 | order type | 来源 |
|---|---|---|
| 默认入场 | `Gtc`（限价挂单）或 `Gtd { expiration = now + entry.cancel_on_timeout_secs }`（cancel-on-timeout） | `EntryOrderSpec.order_type`（从 rec `EntryPlan` 投影；默认 GTD 带超时） |
| 即时流动性 | `Fok` | 仅当 recommendation `EntryPlan.trigger_kind == Immediate` 且显式要求 immediate liquidity |

- **不再默认 FOK-only**（父文档 §5.1）：FOK 是 execution tactic，非架构默认。
- FOK 不重试（[`api/src/infra/retry.rs`](../../../crates/quant-pivot-api/src/infra/retry.rs) §125–131）；
  GTC/GTD 用 `clob_default` 重试策略。
- limit price = `EntryOrderSpec.limit_price`（intent 冻结，approve 可下调）；slippage 已在 admission
  #15 校验。

## 5. submit_if_admitted 流程（父文档 §16.4，claim-first + fail-closed）

```rust
pub async fn submit_if_admitted(intent_id, deps) -> QuantResult<ExecutionOrderInfo> {
    // 0. Pre-check (non-mutating): Approved / ApprovedByPolicy, not expired.
    let intent = deps.intents.find_by_id(intent_id).await?.ok_or(NotSubmittable)?;
    ensure_submittable(&intent, Utc::now())?;

    // 1. Claim txn (double-submit guard): Approved|ApprovedByPolicy -> AdmissionPending (FOR UPDATE).
    deps.submission.claim_for_submission(intent_id, now).await?;

    // 2. Build admission input from the *pre-claim* approval snapshot + evaluate (05.3).
    let input = deps.admission_builder.build(&intent, now).await?;
    let decision = deps.admission.evaluate(input).await?;
    match decision.outcome {
        AdmissionOutcome::Allow => {}
        AdmissionOutcome::Deny => {
            deps.submission.reject_admission(intent_id, reason, trace_ref).await?; // releases capital
            return Err(ExecutionError::AdmissionDenied { reason });
        }
        AdmissionOutcome::Defer => {
            // Transient: revert claim -> Approved (semi_auto) or ApprovedByPolicy (auto).
            deps.submission.revert_claim(intent_id).await?;
            return Err(ExecutionError::AdmissionDeferred { reason });
        }
    }

    // 3. Write-ahead txn: execution_order(state=Submitted) + capital Allocated->Locked
    //    + intent AdmissionPending->Submitted + recommendation -> Executed.
    let order = deps.submission.create_entry_order_and_lock_capital(new_order).await?;

    // 4. Venue submit (NO DB lock — network I/O outside any transaction).
    let venue = deps.order_client.submit(venue_order).await;

    // 5. Settle txn: entry state + capital + position + intent + enqueue recon; breaker.observe_venue.
    deps.submission.record_submission_result(order.id(), ledger_write).await
}
```

**结果落库（步骤 5，事务）按 venue 响应分支：**

| venue 响应 | entry state | capital | position | 对账 |
|---|---|---|---|---|
| `Filled`（全成） | `Filled` | `locked → spent`（spent = cost + fee） | `upsert_from_fill`（open/加权平均） | enqueue（确认成交） |
| `PartiallyFilled` | `PartiallyFilled` | 部分 `spent`，余 `locked`（GTC 挂单）/ `released`（FOK 余量取消） | `upsert_from_fill`（部分） | enqueue |
| `Open`（GTC/GTD 挂单未成） | `Accepted` | 保持 `locked` | 不写 | 由 05.5 轮询/超时对账 |
| `Rejected` | `Failed` | `locked → released` | 不写 | enqueue（确认未成） |
| `Cancelled`/`Expired` | `Cancelled` | `locked → released` | 不写 | enqueue |
| **网络错误/超时/响应歧义** | `Ambiguous` | 保持 `locked`（**不**释放，可能已成交） | 不写 | **必 enqueue**（对账定真相，父文档 §5.2） |

- **`Ambiguous` 是最危险态**（父文档 §5.2）：提交后未确认（超时/连接断/响应不可解析），**不自动计
  失败**、**不释放 capital**、**不写 position**，立即 enqueue 对账（05.5），由场内真值定夺
  （filled → 补 spent + position；not_filled → 释放）。
- recommendation status：`Submitted` 后 `RecommendationStatus::IntentCreated → Executed`
  （[`enums/quant.rs`](../../../crates/quant-pivot-models/src/enums/quant.rs) §71–78）。
- **create 门禁（05.4 收尾）**：`create_with_allocation` / `create_at` 双层防御 — (A) recommendation
  须为 `Published | IntentCreated`；(B) 同 rec 不得存在 `BLOCKING_INTENT_STATUSES` intent（含
  `Submitted` / `PartiallyFilled`）。create 时 `Published → IntentCreated`。
- **fee 账本（05.4 收尾）**：`ClobOrderClient` 用 `FeeCalculator` derive taker fee；`spent_usd` /
  `position.cost_usd` = fill cost + `fee_paid`。
- **FOK 全有全无（05.4 收尾）**：Polymarket FOK 无 partial；API 层 `VenueOrderStatus::PartiallyFilled`
  仅标记响应体 fill ratio 异常；dispatcher 在 venue 返回后调用
  `VenueSubmitResult::with_order_type_semantics` → `Ambiguous`（Hold + recon），不走 GTC 的 `SettlePartial`。

## 6. dispatcher 触发模式（semi_auto vs auto）

- **semi_auto**：approve 后**不自动提交**；提交由 operator 显式触发（`POST /api/quant/intents/{id}/submit`，
  RBAC `OrderIntent:Submit`，operator），或由 auto 提交 worker 在 approved 后短延迟提交（默认人工
  触发更稳；本期默认显式 submit 路由）。
- **auto_execution**：`ApprovedByPolicy` intent 由 `ExecutionDispatcher` worker（`TaskId::ExecutionDispatcher`，
  PeriodicTask）拉取 → `submit_if_admitted`。worker 单实例 + advisory lock 防并发（多副本留 Phase 8+）。

## 6.5 执行熔断器（`ExecutionBreaker`，自动 trip kill-switch）

> 拍板基线（README §5 + 用户确认 `yes_full`）：执行链需要一个**自动熔断器**，在运行时安全信号
> 恶化时**自动收紧 kill-switch**，而不是只靠人工。kill-switch 仍是**唯一权威运营态**；breaker 只是
> 它的**自动触发器**（所有状态变更都经 `KillSwitchControl.set` 落库 + op-log + status/WS 广播，
> `actor = "system:execution_breaker"`）。05.3 admission 是**无状态**的；breaker 是承载"跨决策累计
> 状态"的唯一组件，二者职责严格分离。

### 6.5.1 组件与数据流

```text
venue submit/cancel 结果 (05.4) ─┐
unresolvable recon 计数 (05.5)  ─┼─▶ ExecutionBreaker(滚动窗口 + 滞回)
日内已实现亏损 (05.6)            ─┘        │
                                          ├─▶ VenueHealthHandle(ArcSwap<VenueHealth: Healthy|Degraded>) ─▶ admission #18 热读(仅 defer)
                                          └─▶ 阈值击穿 → KillSwitchControl.set(ExecutionHalted, latch, ack 必需) ─▶ admission #17 权威 deny
```

- 位置：`crates/quant-pivot-core/src/execution/breaker.rs`。内部累计态用 `Mutex` 保护（低频，非热路径）；
  对外发布两路只读输出：`VenueHealthHandle`（`ArcSwap<VenueHealth>`，admission `#18` 零锁热读）+
  通过持有的 `Arc<dyn KillSwitchPort>`（即 05.1 `KillSwitchControl`）执行升级。
- **SSOT 收敛（latch 唯一归属 kill-switch）**：breaker 退化为**纯瞬态 venue-health 累计器**，只发布
  `Healthy` / `Degraded`，**不**再自带 latched `Halted` 内存态（旧设计里它与 kill-switch 形成两个
  latch 真相源，operator 清了 kill-switch 后 breaker 内存 Halted 仍 deny `#18`，只能重启恢复——已修）。
  - **瞬态退化** → `VenueHealth::Degraded`（admission `#18` 判 **defer**，可重试），按 cooldown 自动
    回 `Healthy`，**不**动 kill-switch；
  - **持续失败 / 硬触发** → trip kill-switch 到 `execution_halted`（**latch**，须 operator ack 才能解除——
    复用 05.1 ack 语义）。权威 **deny** 来自 admission `#17`（读 kill-switch），`#18` 不再 deny。trip 后
    breaker 保持 `Degraded`；operator 清除 kill-switch（恢复到可入场态）后，下一次
    `ExecutionBreaker::tick` 观测到即重置失败窗口回 `Healthy`（无需重启）。

### 6.5.2 触发维度（本期 05.4 落 venue 维度；recon/亏损维度随对应子phase接入）

| 维度 | 信号源 | 退化(Degraded→`#18` defer) | 熔断(trip kill-switch → `#17` deny) | feed 落地 |
|---|---|---|---|---|
| venue 健康 | 提交/撤单结果（`VenueSubmitResult`/`ApiError`） | 滚动窗口内连续失败 ≥ `venue_consecutive_failures_to_degrade` | 连续失败 ≥ `venue_consecutive_failures_to_halt`，或窗口 error-rate ≥ `venue_error_rate_bps_to_halt`（breaker 保持 Degraded，权威 deny 由 `#17` kill-switch） | **05.4（本期）** |
| 对账不可解 | `ReconciliationRepository::has_unresolvable` / 新增 unresolvable 事件 | — | auto_execution 下任一 unresolvable（与 admission `#17` 同义，breaker 额外把它**升级为 latch**，阻断后续所有自动入场直至人工） | **05.5** |
| 日内已实现亏损 | 05.6 退出 realized PnL + 05.4 fills 派生的日内累计亏损 | 接近上限（≥ 80% cap）→ Degraded | 日内 realized loss ≥ `daily_realized_loss_cap_usd` | **05.6** |

- venue 成功一次即重置连续失败计数；窗口用单调时间裸滑动（无 wall-clock 依赖之外的随机）。
- breaker 每次状态跃迁写 op-log（经 `KillSwitchControl`）并 `set_auto_execution_halted` metric 已由
  05.1 覆盖；新增 `quant_execution_breaker_trips_total{dimension}`。

### 6.5.3 恢复语义

- `Degraded → Healthy`（未 trip）：无失败持续 `cooldown_secs` 后自动恢复（admission 自然停止 defer）。
- trip 后：kill-switch `execution_halted` latch **只能** operator 经 `POST /api/system/kill-switch`
  （ack=true）显式解除（05.1）。breaker 自身不自动解除 kill-switch（钱相关 fail-closed）；它只在
  `tick` 中观测到 kill-switch 已被清回可入场态后，重置自己的失败窗口（SSOT：latch 归 kill-switch，
  breaker 不持有第二份 latch）。
- 进程重启：breaker 内存态天然为空（启动 `Healthy`）；若 kill-switch 持久态仍为 `execution_halted`，
  `#17` 继续 deny（权威），无需把 breaker 从 kill-switch 派生。

### 6.5.4 接线（boot）

- `ExecutionBreaker::new(KillSwitchControl handle, ExecutionBreakerConfig from runtime-config)`；
  `VenueHealthHandle` 注入 `AdmissionInputBuilder`（替换 05.3 占位 `VenueHealth::Healthy`）。
- venue 结果回报点：`CoreExecutionDispatcher.record_submission_result` 成功/失败后调用
  `breaker.observe_venue(outcome)`。
- config 段见 [`06-config-deploy-and-ops.md`](../06-config-deploy-and-ops.md)：`execution.breaker.*`。

## 8. 生产不变量与失败语义

- **唯一桥梁**：提交必经 intent + admission；无 intent / 未 admitted 不可下单（无旁路 venue 调用）。
- **行锁防双提交**：`get_for_update` + 状态机校验保证同一 intent 不被并发提交两次。
- **网络 I/O 不持 DB 锁**：admission allow 后先在事务内建单 + lock capital（提交意图持久化），venue
  调用在事务外；响应后再事务内记录（避免长事务持锁）。
- **Ambiguous fail-closed**：提交未确认绝不释放 capital、绝不计失败、必入对账（宁可锁住资金等对账，
  也不放走可能已成交的钱）。
- **capital 守恒**：`locked` 后只能 → `spent`（fill）/ `released`（确认未成）/ `impaired`（对账不可
  恢复）；任意路径金额守恒（05.0 §6）。
- **position 账本真相源**：fill 驱动 `upsert_from_fill`（加权平均 avg_price、累计 cost+fee）；
  position 与 capital `spent` 同事务。
- **可恢复**：进程崩溃后 boot 扫描 `Submitted`/`Ambiguous` 无终态订单 → 交对账（05.5）；capital 恢复
  失败 → `Impaired` + 人工，执行 fail closed，报告可继续（父文档 §9）。
- **FOK 不重试**；GTC/GTD 幂等提交（venue 幂等键 = intent id 派生，防重复下单）。
- **money newtype**：`Price`/`Shares`/`Usd` 全程；`f64` 仅 venue SDK 边界（façade 内转换）。
- **错误分层**：`ExecutionError::{AdmissionDenied, AdmissionDeferred, NotSubmittable, CapitalRecoveryFailed}`；venue
  错误经 `ApiError` façade → `QuantError::Api`；web 映射：`AdmissionDenied`/`NotSubmittable` → 409；
  `AdmissionDeferred` → 503（可重试，intent 保持 submittable）。

## 11. Blocker

- 若存在任何绕过 intent/admission 的下单路径，失败。
- 若 `Ambiguous` 释放 capital 或计为失败，失败。
- 若同一 intent 可并发双提交，失败。
- 若 capital 在任一提交分支破坏守恒，失败。
- 若 venue 网络调用在 DB 事务内（长事务持锁），失败。
- 若 position 账本非 fill 驱动（凭空写入），失败。
- 若引入了额外 arming 开关（违背 README §5.1 拍板），失败。
- 若 SDK 类型泄漏出 `order_client.rs` façade，失败。
