## 1. 目标

`CoreExecutionDispatcher::submit_if_admitted` 是 authorized entry intent 进入 signed venue order 的唯一常规路径。

它必须：

- 只消费 `Authorized` intent，不根据当前 policy 伪造新 evidence。
- 在任何 money write 前运行 canonical admission。
- 先 claim intent/condition，再 write-ahead 持久化 execution identity，最后才调 venue。
- 不在数据库锁或 transaction 中做 network I/O。
- 将 timeout/unknown 编码为 `Ambiguous`，保留 capital 并交 reconciliation 定真。
- 发布的 ClickHouse event 只是 PostgreSQL 事实的异步投影，不反向控制资金。

## 2. Durable queue and wake semantics

PostgreSQL 中的 `Authorized` intent 是 durable work queue。`DispatchWake` 只是 process-local latency hint，可丢失、可合并，不携带 work identity。

- Operator grant 把 `PendingAuthorization` 变为 `Authorized` 后发 wake。
- Active policy 创建已 `Authorized` intent 后发 wake。
- Poll backstop 会重新查询 durable rows，因此进程 crash 不丢 work。
- 无论 authorization kind 是 operator 还是 active policy，都走同一 dispatcher 与 admission。

## 3. Claim-first protocol

```text
1. feature-parity latch pre-check
2. load Authorized, unexpired intent
3. build immutable AdmissionInput from the pre-claim snapshot
4. evaluate admission and prepare exact venue order
5. atomically claim:
   intent Authorized -> AdmissionPending
   entry condition -> Consumed
6. revalidate feature-parity clear generation
7. write-ahead execution order + lock capital
8. call venue outside DB transaction
9. atomically settle venue result + intent/capital/position/reconciliation
```

Admission `Deny` 在 claim 前就把 intent 收敛为 `AdmissionRejected` 并释放 capital。`Defer` 不消费 condition，intent 保持 `Authorized`。

如 claim 后、write-ahead 前的 feature-parity/CAS/preparation 失败，repository 原子执行：

```text
AdmissionPending -> Authorized
Consumed condition -> claimable current state
```

返回 `Authorized` 不改写 `AuthorizationEvidence`。

## 4. Write-ahead transaction

`ExecutionSubmissionRepository::create_entry_order` 在一个 PostgreSQL transaction 内：

- 重新锁定并验证 `AdmissionPending` intent；
- 在 parity advisory lock 下验证 exact clear generation；
- insert `ExecutionOrder(state = Submitted)` 和 immutable prepared-order identity；
- capital `Allocated -> Locked`；
- intent `AdmissionPending -> Submitted`；
- recommendation 进入对应 executed lifecycle；
- 写必要 audit/outbox。

事务 commit 后才允许调 `PolymarketOrderClient`。任何代码都不得先调 venue 再补业务 identity。

## 5. Order semantics

`PreparedVenueOrder` 冻结：

- execution account / wallet topology
- market/token/side
- exact shares 或 cash-budget amount semantics
- limit price / order type / expiration
- tick size / neg-risk metadata
- PIT fee schedule / maker-rebate evidence and hashes
- prepared-at / valid-until

Default entry 是有 limit cap 的 GTC/GTD。Immediate/FOK 只在 recommendation 的 frozen entry plan 明确要求时使用。FOK 不允许 partial-fill success；与 order semantics 矛盾的响应进入 `Ambiguous`，不猜测成交。

Fee 不在 dispatcher 中使用第二套公式重算。Admission/preparation 冻结 PIT expected economics，最终 exact fee 由 finalized `quant_account_chain_execution` 所有。

## 6. Venue result settlement

| Venue outcome | Execution order | Capital / position | Required follow-up |
|---|---|---|---|
| `Filled` | `Filled` | exact spent + position lot update | reconciliation/finality |
| `PartiallyFilled` | `PartiallyFilled` | fill portion spent；remainder locked/released per order semantics | reconciliation |
| accepted/resting | accepted/submitted lifecycle | capital remains locked | polling / timeout handling |
| rejected/cancelled/expired | terminal failure/cancel state | releasable amount released | evidence reconciliation |
| `Ambiguous` | `Ambiguous` | capital remains held；no guessed position | mandatory reconciliation |

`record_submission_result` 在一个 transaction 内更新 order、intent、capital、position lot 和 reconciliation work。Idempotent retry 不能重复计数 cost、fee 或 shares。

## 7. Ambiguous and restart recovery

Venue 调用返回前进程终止、HTTP timeout、响应无法解析或 identity 不完整时：

1. 不得标记 unfilled/failure。
2. 不释放全部 capital。
3. 不用 account balance delta 猜测一个 fill。
4. 不重新生成 order/nonce/signature。
5. 使用持久化的 execution identity 继续 CLOB/account-chain reconciliation。

Boot recovery 查找 dangling `Submitted`/`Ambiguous` order，将它们交给 reconciliation，不直接重发。

## 8. Execution breaker and kill switch

`ExecutionBreaker` 累计 venue/reconciliation 健康事实：

- transient venue degradation 只使 admission `Defer`；
- 持续故障由受治理的 runtime-control 路径 latch kill switch；
- kill switch 是唯一运营禁单，breaker 不保留第二个“halted”权威状态。

## 9. Observability

- order submitted / result / ambiguous / reconciliation-required metrics 使用 closed labels。
- intent/order lifecycle event 只在 PostgreSQL commit 后发布。
- CH event writer 失败不回滚已 commit 的 PG money truth，而是进入可观测重试/告警。
- 不记录 private key、raw signature、credential 或 PII。

## 10. 验收

- 并发 claim 只有一个成功，intent/condition 不出现半 transition。
- Deny/Defer/Allow 分支的 intent/capital/condition 终态精确。
- Feature-parity latch 在 pre-claim 与 write-ahead transaction 两次验证，覆盖 race。
- Venue 调用期间无 DB lock，timeout-after-submit 与 restart 只消费已持久化 identity。
- Filled/partial/rejected/cancelled/ambiguous 的 capital、position、intent、reconciliation 原子收敛。
- Operator-authorized 与 active-policy-authorized intents 都走相同 admission/submission path。
- 不运行真实 venue canary 也可闭合 Implementation E2E；Operational Activation 必须独立授权。
