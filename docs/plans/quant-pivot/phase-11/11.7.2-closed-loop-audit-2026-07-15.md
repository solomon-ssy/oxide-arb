### 0.3 补齐的科学与垂直证据

- `ResearchPolicyFitter` 使 profile 能力显式化：无 producer 的 pooled profile 在 preflight 以
  `ProfileFitterUnavailable` fail-closed；Weather profile 才能进入 fitter。
- Weather source gate 真实实现 AWC METAR/SPECI/COR 对 GHCNh daily-high proxy 验证，包含
  latest-revision、station/date support、availability、Wilson lower bound、revision-chain 与方法 hash；
  `gaps_recovered=false` 或任一支持门槛失败即阻断。
- structural volatility 作为第九类 sealed **风险证据**，不是 entry candidate：只移植论文 DR/DR-AS
  函数形式，基于 Polymarket PIT mid/bid/ask/TTR 与 reconciled trailing-hour volume，在 causal 48-active-update
  warm-up 后做 monthly expanding-window OOS、volume-weighted Gaussian QML 非负 `K`、clipped 95%
  interval、volume-weighted Winkler score/coverage；绝不移植 Kalshi 系数。
- `ResearchOnly` activation 从 evaluation track 派生，不能 Publish；11.7.2 不制造伪 SemiAuto canary。
- 统一 PnL 语义明确区分 counterfactual 与 actual：entry/model replay/Policy replay 共用纯 walk；Sell lot
  replay 消费 labeler 已用共享 sell walk 冻结的标签；attribution 锚定 venue fill/position/capital ledger，
  不用事后盘口重写真实成交。该边界避免重复 walk 与 hindsight bias，同时保留 fee schedule / book lineage。

### 4.6 Structural volatility OOS — MISSING

- 收尾台账 Wave 3 明确未勾。  
- 仅 `execution_pg_seed.rs` 中 `methodology_id: "test-only-structural-volatility-v1"` fixture —— **不是 producer**。

## 5. 执行 / fee / 回放深度核验

### 5.1 Cash-budget engine — PARTIAL

共享引擎：`quant-pivot-research/src/execution_semantics.rs`

- BUY：`walk_buy_cash_budget` → `gross + fee <= cash_budget`  
- SELL：`walk_sell_exact_shares`，fee 从 proceeds 扣除  

| 消费者 | 是否共用 walk |
|---|---|
| Admission / prepare | 是 |
| Composer report sizing (BUY) | 是（但 fee schedule 被破坏，见下） |
| Policy replay Fit/Validate | 是 |
| Exit prepare | 是（SELL） |
| Training labeler exit | 是（SELL，builder 被清零） |
| Kelly allocation / planner | **否**（Kelly USD 后再 snap tier） |
| Backtest simulator | **否**（fee-ignorant PnL） |
| Attribution | **否** |
| Reconciliation | 用 `PitFeeSchedule::fee`，非 book-walk |

与 Polymarket V2「market buy 用余额做 fee-adjusted fill」意图一致；但未端到端收敛。

### 5.2 PreparedVenueOrder exact-submit — COMPLETE

Dispatcher 从 prepared 冻结字段构造 `VenueOrder`（price / amount / expected_fee / fee_schedule_hash），提交路径不重算。  
Admission 时基于 live book + PIT info **一次性**冻结 —— 正确。

### 5.3 PIT ClobMarketInfoVersion — COMPLETE（有残留）

- Worker：单次 HTTP + raw/SDK 同字节二次反序列化  
- Append-only + content-addressed `(market_id, payload_hash)`  
- 双时态 PIT 读：`effective_at` / `available_at`  
- `fd` + builder rates 强制；缺失 / mismatch fail-closed  
- Category fee fallback / `FeeSource::CategoryDefault` 已删  

残留：进程内 `FeeCalculator` rate cache 仍被 worker 写入；生产 quote 路径基本死代码，应删除而非保留第二真相。

### 5.4 P0：fee 语义撕裂（本 phase 最高优先级）

**现象：**

```text
composer.rs / labeler.rs:
  builder_maker_fee_bps = ZERO
  builder_taker_fee_bps = ZERO
  builder_attributed = false

admission/builder.rs / trade_policy_replay.rs:
  保留真实 mbf/tbf
  builder_attributed = false（且 core 中从未出现 true）
```

**对照官方文档（[Builder Fees](https://docs.polymarket.com/builders/fees)）：**

- 有 `builderCode`：用户付 platform + builder（additive）  
- 无 `builderCode`：不收 builder  

**问题本质：**

1. Report sizing / training label **系统性低估成本**（相对 admission/replay 所掌握的 schedule rates）。  
2. `builder_attributed` 全链路恒 false —— 若未来挂 builder code，研究与 live 都会漏计 builder fee；若永不挂，则强制采集 `mbf`/`tbf` 半接线。  
3. 双公式：`api/fees/formula.rs` vs `PitFeeSchedule::fee`。  
4. Report 仍用窄类型 `MarketFeeSchedule`（无 builder 字段）。  

这直接违反计划 §4.1「Allocation、report sizing、simulator、composer、admission…必须收敛到同一执行语义」。

### 5.5 Reconciliation fee provenance — PARTIAL

优先级：`OnChainExact` > `AuthenticatedTradeReconstructed` > `PreparedScheduleExpected`  

- expected / observed 列分离；expected **不覆盖** `observed_fee_usd` —— 好。  
- `applied = observed.unwrap_or(expected)`：无观测时 ledger 用 expected —— 对资本结算可理解，但「expected 不得伪装成 venue fact」在 cash 层仅部分满足。  
- Dispatcher/exit 立即路径仍用 `expected_fee` 写 `cost_usd`，待 recon 升级。

### 5.6 Dataset fee — PARTIAL

- PolicyFit / sealed：`build_with_frozen_source` → Source Slice CLOB info —— 正确。  
- 公共 Dataset `/build`：仍 `clob_market_info_repo.window(...)` 读 live PG（PIT 过滤，但非 sealed slice）。  
- Labeler 即便拿到正确平台费率，也将 builder 置零。

### 5.7 Opportunistic sell — PARTIAL（11.7 §12 待迁移）

- 阈值主体来自 frozen intent exit policy。  
- Runtime 仍控制 `enabled` / `shadow_mode` / `max_cumulative_exit_pct`（可收紧 frozen）。  
- 若 11.7.2 声称「策略阈值冻结进 policy」，则此项仍属本 phase 收口缺口。

## 8. 做得好、应坚持的实践

1. **不可变 Research Profile** 作为 horizon / tier / publication gate 唯一真相；Runtime 只保留资源上限与生产证据窗口。
