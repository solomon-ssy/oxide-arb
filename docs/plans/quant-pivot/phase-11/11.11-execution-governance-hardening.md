## 1. 目标与闭环定位

把运行模式升级 preflight 里的两个"占位健康检查"升级为**真实的实时探针**,让"从 report_only 升到
semi_auto/auto_execution"这个治理动作真正 fail-closed:只有当下单通道确实可连、退出监控确实健康时才
允许升级。它硬化执行治理的**真相性**(与全仓 fail-closed 精神一致)。

## 3. 契约与算法设计

### 3.1 Order client 实时探针(#22)

```rust
/// Real connectivity/auth/latency probe for the venue order path. Used by mode
/// preflight (upgrade gate) AND admission #21 (CredentialReadiness) — one truth.
pub trait OrderClientReadinessProbe {
    async fn probe(&self) -> QuantResult<OrderClientReadiness>;
}

pub struct OrderClientReadiness {
    pub reachable: bool,            // 真实轻量 CLOB 请求成功(如 auth ping / server time)
    pub authenticated: bool,        // L2 凭证有效
    pub clock_skew_ms: i64,         // 本地 vs 服务器时钟偏移(下单签名有效期敏感)
    pub rtt_ms: u64,                // 往返延迟
    pub checked_at: DateTime<Utc>,
}
```

- 探针做一次**真实轻量调用**(如 CLOB server-time / auth 校验),不只是"keystore 存在 + URL 非空"。
- 时钟偏移超阈值 → 不 ready(EIP-712 GTD 到期/签名有效期对时钟敏感)。
- 结果缓存 + TTL,避免升级动作打爆 venue;但 TTL 内过期即视为 not-ready。

### 3.2 Exit monitor 实时健康(#22)

```rust
pub struct ExitMonitorHealth {
    pub last_pass_at: DateTime<Utc>,
    pub pass_latency_ms: u64,        // 上一轮扫描耗时
    pub open_lots_covered: u64,      // 覆盖的开放 lot 数
    pub open_lots_total: u64,        // 应覆盖总数
    pub stale: bool,                 // last_pass 超 2×monitor_interval
}
```

- ready 判据:`!stale` 且 `open_lots_covered == open_lots_total` 且 `pass_latency` 在预算内。
- 覆盖率 < 100%(有 lot 未被扫描)→ not-ready → 阻止升到 auto_execution(因为有仓位没人看着退出)。

### 3.3 统一到 preflight 与 admission

- `ModePreflight` 的 `order_client_ready` / `exit_monitor_health` 改为调用 §3.1/§3.2 探针真相。
- admission #21(CredentialReadiness)、#20(ExitMonitorReadiness)复用同一探针结果(单一真相源,
  避免 preflight 与 admission 判据漂移)。

### 3.4 Report run/gap retention 决策（11.8 输入）

- 输入固定为 11.8 的 `quant_report_run` / append-only `quant_report_schedule_gap` schema、ReportOnly
  24h shadow 实际增长率、表/索引体积、p95 health/page 查询延迟和合规审计窗口。
- 默认决策是继续无限期保留；仅当容量或查询 SLO 有实测越界，才允许设计按时间分区与 WORM 冷归档。
- 任何删除前必须有逐分区 row count、canonical digest、对象存储 manifest、restore drill 与 operation log；
  restore 未演练通过时不得 detach/drop。`quant_report_schedule_state` 的 active cursor 永不归档。
- 本 phase 只作有证据的 retention 决策与 go-live 验收，不把 retention 变成 Runtime config 开关，
  不改变 11.8 的 current/publication/lease 语义。

## 6. 生产不变量与失败语义

- **升级 fail-closed**:探针失败/过期/时钟偏移超阈值/退出覆盖不全 → 升级到 semi_auto/auto 被拒
  (`ModePreflightDenied`,带具体探针原因)。
- **单一真相源**:preflight 与 admission 用同一探针结果,禁止两套判据。
- **不打爆 venue**:探针有 TTL 缓存;但过期即 not-ready,不用陈旧结果放行升级。
- **可审计**:探针结果与升级决策关联,写审计(与既有 operation log 一致)。

## 8.1 真实 `$25` closed-loop canary（11.7.2 shadow 之后）

前置条件全部 fail closed：

- 连续至少 24 小时 ReportOnly；所有调度 report facts 均为 `Verified`，conservation 误差为零，且无未解释的 L2 gap、fee、lineage 或事实投递重试；
- 目标 policy 已完成真实 fitter、独立 Validate、Publish，且精确绑定当前 model/runtime/profile/source slice/evidence；
- 本文实时 order-client、clock-skew、exit-monitor coverage、kill-switch 探针全部 ready；
- operator 以单一管理员 scope 提交明确 reason 与 bounded canary approval，审计绑定 policy/report/recommendation/prepared order。

唯一允许的 canary 语义：

- 一次 `$25` 最大总现金支出的 FAK limit BUY；金额包含全部 expected fee，不允许扩大 gross；
- 不自动重试，不将 ambiguous response 当作未成交重发；仅 reconciliation 可以消歧；
- SELL 上限严格等于 venue 已确认实际成交 shares，禁止按请求 shares 或预期 shares 卖出；
- 硬性 gross/net exposure、最大损失、holding-time 与单 market 上限；任何越界、数据 stale、exit monitor gap 或 fee/lineage mismatch 立即进入 kill-switch/manual resolution；
- 完整采集 `submit → ack → match → chain-confirm` 的 `VenueLatencyProfileV1`、`VenueFillObservation`、actual fee、expected/venue cash delta、realized PnL 与 reconciliation provenance。

canary 成功只允许首次 `SemiAuto` 激活。`AutoExecution` 还必须具备真实 Venue latency profile、退出监控全覆盖、kill-switch 演练、无未解释 reconciliation，以及后续独立 soak；不得由 ReportOnly 或单次 canary 直接激活。

## 9. Blocker

- preflight 仍用 boot/spawn 占位而非实时探针。
- preflight 与 admission 判据不一致(两套真相)。
- 陈旧探针结果被用于放行升级。

## 10. 延后 / 缺口

- 多副本一致的 mode/kill-switch(leader-elected)在 Phase 8+。
- venue 级下单幂等键(审计报告 execution 平面残留项,非 23 点内)可在本子phase顺带评估,但主交付是探针。
- canary 后的 `AutoExecution` soak 时长、资金上限提升阶梯与 rollback drill 必须在首次 canary 证据完成后按真实 VenueLatencyProfile 冻结；不得预先用 shadow latency 代替。
- 回指审计点:#22 在此闭合。
