# 04.3 — Report Scheduler

> 父：[`README.md`](README.md) · 概念规格（权威）：[`../04-topn-report-and-recommendation.md`](../04-topn-report-and-recommendation.md) §23–§25、
> [`../08-third-party-crates-and-ml-stack.md`](../08-third-party-crates-and-ml-stack.md) §8、
> [`../00-quant-pivot-architecture.md`](../00-quant-pivot-architecture.md) §10
>
> 闭环定位：**调度闭环**。决定"何时生成报告"——多 schedule cron/interval/ad-hoc fire，
> 经 `ReportScheduleRunner` 封装 `tokio-cron-scheduler`，调用 04.2 lifecycle。**不**决定
> "生成什么"。

## 1. 目标与闭环定位

1. `core/src/infra/schedule/` 薄封装 `tokio-cron-scheduler`；业务层
   （`ReportBuilder`/`ReportLifecycleService`）**不得**直接依赖该 crate。
2. `ReportScheduleRunner` trait + `TokioCronScheduleRunner`：interval / cron / one-shot
   fire；运行时 add/remove job（对应 runtime-config activation diff）。
3. overlap：per-`schedule_id` skip-if-running（量化报告不排队过时 `as_of`）。
4. `AppRunner` 注册唯一 `TaskId::ReportGenerator`；shutdown 分阶段 drain。
5. runtime-config activation 后 `sync_from_config` 动态 rebuild jobs（不重启进程）。
6. report TTL/expire sweep 用 `PeriodicTask`（与 fire 调度解耦）。

## 3. 新领域类型 / 表 / ClickHouse fact

- 无新表 / 无 CH fact。
- 新类型：`ScheduleOverlapGuard`（per-`schedule_id` 异步锁）、`ReportSchedulerDeps`
  （`executor` + overlap + inflight `TaskTracker` + metrics + alerts）、
  `ScheduledReportExecutor`（report pipeline 端口，`ReportLifecycleService` 实现，
  scheduler 不直接依赖 lifecycle 具体类型，便于 fake 测试）。
- **`AdHocReportRequest` 复用既有 `core/src/report/lifecycle.rs` 的类型**（含
  `request_id` 幂等键），**非净新增**；scheduler 经 `executor.run_ad_hoc` 走与 scheduled
  共用的 `run()` 内部路径，幂等键 `ad_hoc:{request_id}`。
- repo 新增只读查询 `RecommendationReportRepository::find_expirable(published_before, limit)`
  + lifecycle `expire_due_reports(now, ttl_secs, limit)`（TTL sweep）。
- `TaskId::ReportExpireSweep`（新 TaskId 变体，`TaskKind::ReportScheduler` → Execution
  stage）承载与 fire 解耦的 expire sweep `PeriodicTask`。

## 4. deploy-config key 与 runtime-config v3 path

- `reports.schedules[]`（`schedule_id` / `cadence` / `top_n` / `knowledge_lag_secs` /
  `enabled` / `model_version_ref` / `market_filter_ref`）—— 04.0 已 cadence 化。
- `reports.ad_hoc_report_enabled`（治理 `POST /api/quant/reports/run`）。
- 有效期是**数据驱动**：每条 recommendation 的 `valid_until` 由模型 `suggested_horizon_secs`
  （被 `time_to_resolution` 封顶）× `reports.entry_window_ratio` 推出（`suggested==0` 时回退到
  `reports.fallback_horizon_secs`）；报告 `valid_until = max(recommendation.valid_until)`。**不再有**
  扁平 `report_ttl_secs`（已删除）。报告在其所有 recommendation 终态后上卷为 `Expired`。
- deploy：`deploy.quant.workers.report_expire_sweep_secs`（驱动 recommendation 过期 sweep / deadline
  scheduler 的 reconcile 兜底 cadence + report 上卷兜底，默认 300）。report 主触发由
  `tokio-cron-scheduler` 承担，**无** tick key。

## 5. 必建模块与 trait

```text

`QuantError::Config`；scheduler backend 生命周期失败 → `SchedulerError::Backend`；
Job 构建被拒 → `SchedulerError::InvalidJobSpec`（在 `runner.rs` / `job_factory.rs`

crates/quant-pivot-core/src/report/

```

### 5.1 `ReportScheduleRunner` trait（父文档 §23.3 权威）

`#[async_trait]`（需 `Arc<dyn>` 供 web/applicator 共享）：

```rust
#[async_trait]
pub trait ReportScheduleRunner: Send + Sync {
    /// 幂等 upsert 一个 schedule（interval/cron；disabled → remove）。
    async fn upsert(&self, schedule: &ReportScheduleConfig) -> QuantResult<()>;
    /// 按 id 移除。
    async fn remove(&self, schedule_id: &str) -> QuantResult<()>;
    /// 从 active runtime-config 快照重建全部 jobs（含删除已移除/禁用的 schedule）。
    async fn sync_from_config(&self, reports: &ReportsConfig) -> QuantResult<()>;
    /// 入队一次性 ad-hoc run（API POST /reports/run）。
    async fn enqueue_ad_hoc(&self, request: AdHocReportRequest) -> QuantResult<()>;
    /// 运行直到取消；与 AppRunner shutdown token 集成（含 in-flight drain）。
    async fn run(&self, shutdown: CancellationToken) -> QuantResult<()>;
}
```

scheduler 经 `ScheduledReportExecutor` 端口调用报告管线（`run_scheduled` /
`run_ad_hoc`），由 `ReportLifecycleService` 实现；scheduler **提供 `trigger_time =
Utc::now()`**（owns clock），`as_of` / version freeze 在 builder 内完成（统一口径）。

### 5.2 `job_factory`（cadence → Job）

```text
ScheduleCadence::Interval{ interval_secs } → Job::new_repeated(Duration)
ScheduleCadence::Cron{ expr, timezone }    → Job::new_cron_job_async_tz（croner，IANA tz）
ad-hoc                                      → Job::new_one_shot（instant）
```

job closure 内（per `schedule_id`，sync dispatch + spawn-to-tracker）：

```rust
fn dispatch_scheduled_fire(schedule_id: &Arc<str>, deps: &Arc<ReportSchedulerDeps>) {
    let Some(guard) = deps.overlap.try_acquire(schedule_id) else {
        deps.metrics.inc_report_schedule_skipped_overlap(schedule_id); // skip-if-running
        return;
    };
    deps.inflight.spawn(async move {
        let _guard = guard;                              // 持锁直到 build 结束
        // trigger_time = Utc::now()；as_of/version freeze 在 builder 内统一完成
        let req = ScheduledReportRequest { schedule_id, trigger_time: Utc::now() };
        match deps.executor.run_scheduled(req).await {
            Ok(report) => deps.metrics.record_report_schedule_fire(id, outcome(&report), elapsed),
            Err(e) => {                                  // 失败隔离：不 panic
                deps.metrics.record_report_schedule_fire(id, "error", elapsed);
                deps.alerts.dispatch_background(report_generation_failed_alert(id, &e));
            }
        }
    });
}
```

### 5.3 overlap（§23.6）

| 策略 | 默认 | 说明 |
|---|---|---|
| Skip if running | ✓ | 同 `schedule_id` in-flight 则跳过 |
| Coalesce to latest | ✗ | 不排队过时 `as_of` |
| Fire all missed | ✗ | 避免 `as_of` 堆积 + duplicate TopN |

`overlap.rs`：per-`schedule_id` `tokio::sync::Mutex` 的 `try_lock`；指标
`quant_report_schedule_skipped_overlap_total{schedule_id}`。

### 5.4 wiring（`scheduler.rs` + `AppRunner`）

```rust
// AppRunner 只注册一个 TaskId::ReportGenerator（TaskKind::ReportScheduler → Execution stage）
runner.spawn(TaskId::ReportGenerator, move |token| async move {
    runner_impl.sync_from_config(&active_reports).await.ok();  // 启动重建 jobs
    let _ = runner_impl.run(token).await;                      // scheduler.start → cancelled → shutdown
});
```

- 启动：`bootstrap.rs` 在 `register_*` 系列中新增 `register_report_scheduler`（spawn
  `TaskId::ReportGenerator`：先 `sync_from_config(active.reports)` 重建 jobs，再 `run(token)`；
  重启后恢复，无需 scheduler 持久化）。
- shutdown：`run()` 收到 cancel 后 `scheduler.shutdown().await` 先停 fire，再
  `inflight.close(); inflight.wait().await` 等待 in-flight report build drain。
  fire job closure 把实际 build **spawn 到 runner 自持的 `TaskTracker`**（不依赖
  `tokio-cron-scheduler` drain 在途 job future），受 Execution stage 预算约束。
- 过期：每条 recommendation 在其数据驱动 `valid_until` 到点过期——`RecommendationDeadlineScheduler`
  （`DelayQueue`）精确唤醒 + `RecommendationExpireSweep`（`PeriodicTask`）兜底，调
  `ReportLifecycleService::expire_due_recommendations`（逐条 `Expired` + cascade 释放该建议 intent
  的 capital + 报告上卷）。`register_report_expire_sweep`（`TaskId::ReportExpireSweep`）是报告上卷
  兜底（按 `report.valid_until` 且全终态）。cadence = `deploy.quant.workers.report_expire_sweep_secs`，
  与 fire 解耦。

### 5.5 ad-hoc（§23.7）

`POST /api/quant/reports/run`（04.4）→ `enqueue_ad_hoc` → `Job::new_one_shot_async`；受
`reports.ad_hoc_report_enabled` 治理（在 builder `resolve_knowledge_lag` 内 fail closed）；
经 `executor.run_ad_hoc` 与 scheduled fire **共用** lifecycle 内部 `run()` 路径（幂等键
`ad_hoc:{request_id}`）。ad-hoc 不走 overlap guard（`request_id` 唯一），但同样 spawn 到
in-flight `TaskTracker` 以保证 graceful drain。

## 6. 生产不变量与失败语义

- **薄封装隔离**：仅 `infra/schedule/` 依赖 `tokio-cron-scheduler`；`research` /
  `web` / 业务 service 禁止直接依赖（架构 lint 校验）。
- **单实例约束**：Phase 4 单 report scheduler 实例；多副本 duplicate fire 属 Phase 8 ops
  （文档化约束，不在本期解决）。
- **`as_of` 冻结在 lifecycle**：scheduler 只触发，`as_of = trigger − knowledge_lag` +
  version freeze 由 `run_scheduled` 统一完成（避免两套口径）。
- **失败隔离**：report 失败仅 metrics + alert，scheduler 继续；绝不 panic、不拖垮 ingest。
- **热更新**：runtime-config activate 改 cadence 后，下一 fire 生效，**不重启进程**。
- **不启用 scheduler 持久化**：`postgres_storage` / `nats_storage` 关闭；schedule 真相源
  是 runtime-config（§23.8）；重启 `sync_from_config(active)` 重建。
- **graceful drain**：shutdown 先停调度，再 drain in-flight 报告（不中断半截事务）。

## 9. Blocker

- 若 `research`/`web`/业务 service 直接依赖 `tokio-cron-scheduler`，本子phase失败。
- 若 report 失败导致 scheduler 退出或 ingest 受影响，失败。
- 若 cadence 热更新需重启进程，失败。
- 若同 `schedule_id` 长 pipeline 重叠产生 duplicate report，失败。
- 若启用 scheduler `postgres_storage`（第二真相源），失败。

## 10. 延后 / 缺口

> 完整索引见 [`README.md`](README.md) §6。

- **多副本 leader-elected report worker** → Phase 8+（`apalis-cron` + Postgres 分布式
  claim 再评估）；本期单实例约束文档化。
- **scheduler 持久化** → 不做（by design，§23.8）。
- **misfire / catch-up 策略** → 不做（量化报告不补发过时 `as_of`）。
- **健康扫描 metrics 补漏 cadence** → 不做；`report_scheduler_tick_secs` 已**删除**并由
  `report_expire_sweep_secs`（仅 expire sweep cadence）取代，不作主触发器。
